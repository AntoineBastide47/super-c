Specification for Super-C: a production-oriented LL(1)-friendly systems language

This document consolidates the full design discussion into a single human-readable specification for Super-C. Super-C is C-like in syntax, control flow, memory layout, pointer access, and native compilation target, but it deliberately rejects ISO C declaration syntax so the grammar can remain LL(1)-friendly.

Language: Super-C Backend: generated C Parser: recursive descent / LL(1) Dispatch: static by default Generated: 2026-06-21

1. Executive summary

Super-C is a planned C-like systems language that transpiles to C and then uses clang, gcc, or MSVC to produce native object code or executables. It adds a small set of high-value features while preserving predictable parsing, C ABI compatibility, and C-level performance. The project is currently a language design and compiler planning project, not an implemented compiler.

Core additions

  • RAII via deterministic destructors.
  • defer for explicit scope-exit actions.
  • Rust-like traits.
  • Bounded generics such as <T: Writer + Drop>.
  • Rust-like match over enums and scalar ranges.
  • Operator overloading for existing built-in operators through traits.
  • No custom symbolic operators and no operator-declaration syntax.

Key constraints

  • Not ISO C-compatible syntax.
  • Declarations must start with keywords.
  • No redefinition of reserved/core syntax operators.
  • No custom operator tokens; only existing built-in operators may be overloaded.
  • No parsing dependency on typedef-like symbol tables.
  • C headers are handled through FFI, not parsed as source language files.

Performance target

  • Zero-cost abstractions where possible.
  • RAII lowers to cleanup calls.
  • Generics monomorphize by default.
  • Traits use static dispatch by default.
  • Dynamic dispatch is explicit with dyn Trait.
Primary conclusion: this language can remain LL(1)-friendly and still provide RAII, defer, traits, bounded generics, match, scalar range cases, optional type annotations, and C++/Rust-style operator overloading for existing built-in operators, provided all major syntactic forms have distinct leading tokens and expression parsing uses a fixed precedence table or Pratt parser.

2. Non-goals and constraints

2.1 Not full C

Full ISO C is not LL(1) in the practical sense needed here. Its declaration syntax can require semantic information, especially around typedef names. 

// C-style ambiguity
T * x;

If T is a typedef name, this can be a declaration. If T is an ordinary identifier, similar token patterns can belong to expressions. A pure LL(1) parser must not need a symbol table to know which grammar production to apply.

Rejected: C-compatible type-first declarations such as int x; or T *x;. They recreate the C parsing problem.

2.2 Required syntactic discipline

  • 1Declarations start with explicit introducers: let, const, fn, struct, enum, trait, impl, type, extern.
  • 2Types and expressions are parsed in distinct syntactic contexts.
  • 3Generic calls use an unambiguous marker, recommended as ::<...>.
  • 4if, while, and match arms use blocks or explicit expression-arm syntax. No dangling-else ambiguity.
  • 5Reserved operator tokens and precedence are fixed by the language.
  • 6Only existing built-in operators may be overloaded, and only through trait resolution.

4.2 Operator token policy

Super-C supports overloading only for existing built-in operators. Operator behavior is resolved by traits during type checking. The lexer does not produce a generic custom-operator token class, and the language has no operator declaration syntax.

+-*/% ==!=<<=>>= &|^~<<>> []()
Rejected: custom spellings such as +-, **, <>, |>, and arbitrary symbolic operators.

4.3 Reserved operator spellings

These tokens are fixed language tokens. They cannot be redefined, shadowed, or repurposed as custom operators.

+-*/%~! ??? =+=-=*=/=%= &=|=^=<<=>>= ==!=<<=>>= &|^&&||<<>> ->=>::....= ///**/
Maximal munch rule: reserved multi-character tokens win. 0..9 tokenizes as 0, .., 9; 0..=9 tokenizes as 0, ..=, 9. ?? tokenizes as the coalesce token, while postfix try uses a single ? token.

7. RAII and defer

7.1 RAII model

RAII is implemented through deterministic scope-exit cleanup. Types that implement Drop receive a destructor call when the value leaves scope, unless the value has been moved. 

trait Drop {
    fn drop(self: *mut Self);
}

7.2 Scope-exit order

  • Cleanup runs in reverse construction order.
  • defer runs in LIFO order.
  • RAII destructors and explicit defers participate in the same scope-exit cleanup sequence.
  • Each match arm and block is its own cleanup scope.

7.3 Source and lowered C

Source

fn f() -> int {
    let file = File.open("x.txt")?;
    defer print("leaving f");

    if bad() {
        return 1;
    }

    return 0;
}

Generated C shape

int f(void) {
    int __ret;
    File file;

    Result_File_IOError __tmp = File_open("x.txt");
    if (__tmp.tag == RESULT_ERR) {
        return __error_return(__tmp.as.err);
    }
    file = __tmp.as.ok;

    if (bad()) {
        __ret = 1;
        goto __cleanup_0;
    }

    __ret = 0;
    goto __cleanup_0;

__cleanup_0:
    print("leaving f");
    File_drop(&file);
    return __ret;
}

8. Traits and generics

8.1 Static traits

Traits define required behavior. Generic functions, structs, enums, impl blocks, and methods can constrain type parameters using trait bounds. Bounds must be enforced by the semantic phase, not by parser decisions. 

trait Writer {
    fn write(self: *mut Self, bytes: []u8) -> usize;
}

trait Drop {
    fn drop(self: *mut Self);
}

fn copy<T: Writer + Drop>(out: T, data: []u8) -> usize {
    let mut file = move out;
    defer file.drop();

    return file.write(data);
}

8.2 Generic positions

8.3 Where clauses

Inline bounds are concise for simple cases. where clauses are preferred for complex bounds or bounds involving multiple generic parameters.

where
    T: Reader + Writer + Drop
{
    // ...
}

8.4 LL(1) constraints for generics

Generic syntax remains LL(1)-friendly if generic parameters appear in declaration/type contexts and explicit generic calls in expression context use a disambiguating marker.

8.5 Monomorphization

By default, generic functions and generic data types are monomorphized. Each concrete instantiation gets a specialized generated C type or function. This is the preferred model for C-level speed. 

// Source
fn write_all<T: Writer>(w: *mut T, data: []u8) {
    w.write(data);
}

// Generated C for File
void write_all_File(File *w, Slice_u8 data) {
    File_write(w, data);
}

// Generated C for Buffer
void write_all_Buffer(Buffer *w, Slice_u8 data) {
    Buffer_write(w, data);
}

8.6 Dynamic traits

Dynamic dispatch should exist only through explicit syntax such as dyn Writer. It lowers to a fat pointer or object pair containing data pointer plus vtable pointer. 

typedef struct {
    void *data;
    const WriterVTable *vtable;
} DynWriter;

8.7 Deferred trait-system features

Associated types, higher-kinded types, generic associated types, specialization, negative bounds, and overlapping implementations should be deferred until the basic trait solver and monomorphization pipeline are stable.

9. Match and patterns

9.1 Tagged enums

Rust-like match should initially focus on tagged enums and scalar patterns. This gives high utility while keeping lowering simple. 

enum Result<T, E> {
    Ok(T),
    Err(E),
}

fn status(r: Result<usize, IOError>) -> int {
    return match r {
        Ok(n) => 0,
        Err(e) => 1,
    };
}

9.2 Lowering

switch (r.tag) {
    case RESULT_OK: {
        size_t n = r.as.ok;
        __match_result = 0;
        break;
    }
    case RESULT_ERR: {
        IOError e = r.as.err;
        __match_result = 1;
        break;
    }
}

9.3 Range cases

Scalar range cases such as '0'..='9' are allowed. They lower to comparisons or compiler-supported switch patterns if the backend can use them portably.

Source

fn classify(c: u8) -> int {
    return match c {
        case '0'..='9' => 1,
        case 'a'..='z' => 2,
        case 'A'..='Z' => 3,
        _ => 0,
    };
}

Portable C lowering

int classify(uint8_t c) {
    if (c >= '0' && c <= '9') return 1;
    else if (c >= 'a' && c <= 'z') return 2;
    else if (c >= 'A' && c <= 'Z') return 3;
    else return 0;
}

10. Operator overloading

10.1 Policy

Super-C supports C++/Rust-style overloading of existing built-in operator tokens only. There are no custom symbolic operators, no operator declarations, no OP2_CUSTOM token class, and no precedence declarations. Operator overloading is a type-checking feature implemented through traits.

QuestionDecisionReason
Overload existing operators such as +, -, *, ==, or []YesThe parser sees a fixed token; the type checker resolves the trait implementation.
Add custom operators such as +-, **, <>, or |>NoThey add lexer, parser, formatter, and readability complexity without being necessary for the core language.
Add operator-declaration syntaxNoThere are no custom operators to declare.
Redefine core syntax such as =, ., ->, &&, ||, move, or deferNoThese encode language semantics, not ordinary overloadable operations.

11.3 Safe wrapper example

struct File {
    handle: *mut CFile,
}

impl File {
    fn open(path: str, mode: str) -> Result<File, IOError> {
        let h = unsafe fopen(path.cstr(), mode.cstr());

        if h == null {
            return Result.Err(IOError.Last());
        }

        return Result.Ok(File { handle: h });
    }
}

impl Drop for File {
    fn drop(self: *mut Self) {
        if self.handle != null {
            unsafe fclose(self.handle);
            self.handle = null;
        }
    }
}

11.4 Binding generation

Do not implement a full C parser for headers. Use Clang, libclang, or clang AST tooling to generate raw FFI declarations. Real C headers contain macros, conditional compilation, compiler extensions, attributes, platform branches, and typedef idioms.

  ↓

  ↓
your-language extern declarations

First safe wrapper families

  • Constants from limits, float, stddef, stdint

12. Performance model

The language can reach ISO C-level speed if abstractions lower to simple C and hidden runtime mechanisms are avoided. The goal is not “C syntax”; it is “C machine-code quality.”

FeatureCan be zero-cost?Condition
RAIIYesLower to explicit cleanup calls.
deferYesLower to explicit cleanup at exits.
TraitsYesStatic dispatch by default.
GenericsYesMonomorphize concrete instantiations.
matchYesLower enum matches to switch, ranges to comparisons.
Operator overloadingYesResolve statically to direct function calls/inlined operations.
Type inferenceYesCompile-time only.

12.1 Hidden costs to avoid

  • 1Mandatory garbage collection.
  • 2Mandatory reference counting.
  • 3Mandatory dynamic trait dispatch.
  • 4Mandatory heap allocation for generic values or enum payloads.
  • 5Mandatory boxing of trait objects.
  • 6Mandatory runtime reflection.
  • 7Implicit string allocation in ordinary expressions.
  • 8Exceptions or unwinding through C frames.

12.2 Recommended defaults

ConceptDefaultExplicit slower/safer alternative
GenericsMonomorphizedDynamic trait objects only when explicitly requested.
TraitsStatic dispatchdyn Trait for vtable dispatch.
ErrorsResult<T, E>Optional panic for unrecoverable failures, but not across C FFI.
StringsPointer + length viewOwned string allocation explicit.
Slices{ ptr, len }Checked indexing in safe mode; unchecked only in unsafe.
HeapExplicit allocationBox<T>, arena, or allocator APIs.
Important advantage: the frontend can know more than C about ownership, moves, non-null references, enum exhaustiveness, and aliasing. If exposed correctly to C codegen, this can sometimes outperform typical handwritten C.

13. C code generation

C code generation should consume a C-shaped IR or C AST produced after semantic lowering and middle-end simplification. The emitter should not contain ownership, trait, or match logic directly; those decisions should already be explicit in MIR or C IR.

13.1 Generated C style

  • Emit simple functions, structs, enums, unions, and explicit cleanup labels.
  • Use #line directives so diagnostics point back to source files.
  • Use stable name mangling to avoid symbol collisions.
  • Use static inline for small generated helpers where appropriate.
  • Preserve const, restrict, alignment, and visibility metadata when semantically valid.
  • Keep generated control flow simple enough for C compiler optimization passes.

14. Safety model

The language can be low-level without pretending C is safe. The correct split is safe-by-default user code with explicit unsafe at the boundary where raw pointers, unchecked indexing, C calls, signal behavior, nonlocal jumps, aliasing promises, or manual lifetime assertions are required.

14.1 Safe by default

  • Move checking prevents use-after-move.
  • Definite initialization prevents reads and drops of uninitialized values.
  • RAII prevents routine resource leaks.
  • Match exhaustiveness prevents missing enum cases.
  • Typed slices carry length.
  • Trait bounds are checked before C code generation.

14.2 Explicitly unsafe

  • Raw C FFI calls.
  • Dereferencing raw pointers.
  • Unchecked indexing.
  • Calling signal-unsafe functions from handlers.
  • setjmp/longjmp interactions with RAII.
  • Manual aliasing or lifetime assertions.
Critical rule: longjmp must not bypass destructors. Either ban it in safe code, wrap it in a constrained unsafe API, or model it as a nonlocal control-flow hazard that invalidates RAII guarantees.

15. Implementation roadmap

15.1 Phase 1 — Core compiler

  • Lexer with fixed keywords, ASCII identifiers, literals, comments, punctuation, and reserved operator tokens.
  • Recursive-descent parser for top-level items, statements, and types.
  • Precedence or Pratt parser for expressions.
  • AST and diagnostic system.
  • C code emission for functions, variables, structs, control flow, and expressions.

15.2 Phase 2 — Type system

  • Built-in numeric, bool, pointer, reference, slice, array, struct, enum, and function types.
  • Optional type annotations with local inference.
  • Type checking for expressions and statements.
  • Name resolution and module-level symbol tables.

15.3 Phase 3 — RAII and defer

  • Drop trait.
  • Scope cleanup stack.
  • Cleanup labels in generated C.
  • Move semantics.
  • Partial move tracking for structs/enums.

15.4 Phase 4 — Traits and generics

  • Trait definitions and impls.
  • Generic parameter parsing and bounds for functions, structs, enums, impls, and methods.
  • Monomorphization of generic functions and generic data types.
  • Operator traits for existing built-in operators.
  • Optional dyn Trait vtable representation.

15.5 Phase 5 — Match

  • Tagged enum representation.
  • Simple variant matching.
  • Wildcard matching.
  • Scalar literal and range matching.
  • Exhaustiveness and overlap checking.

15.6 Phase 6 — Middle-end and C IR

  • HIR and MIR design.
  • Explicit control-flow blocks.
  • Explicit drops, defers, moves, and temporaries.
  • Constant folding and unreachable-code detection.
  • Drop/defer simplification and drop elision after moves.
  • C AST or C IR before text emission.

15.7 Phase 7 — FFI and standard library

  • extern "C" declarations.
  • Opaque and transparent C type support.
  • Clang-based binding generator.
  • Core safe wrappers: IO, allocation, memory, errno, time, threads, atomics.
  • Build-system integration with clang/gcc/MSVC.

16.1 Full sample program

extern "C" {
    type CFile;

    fn fopen(path: *const char, mode: *const char) -> *mut CFile;
    fn fclose(file: *mut CFile) -> int;
    fn fwrite(ptr: *const void, size: usize, count: usize, file: *mut CFile) -> usize;
}

trait Drop {
    fn drop(self: *mut Self);
}

trait Writer {
    fn write(self: *mut Self, bytes: []u8) -> usize;
}

trait Add<Rhs, Out> {
    fn add(self: Self, rhs: Rhs) -> Out;
}

struct File {
    handle: *mut CFile,
}

impl Drop for File {
    fn drop(self: *mut Self) {
        if self.handle != null {
            unsafe fclose(self.handle);
            self.handle = null;
        }
    }
}

impl Writer for File {
    fn write(self: *mut Self, bytes: []u8) -> usize {
        return unsafe fwrite(bytes.ptr, 1, bytes.len, self.handle);
    }
}

enum Result<T, E> {
    Ok(T),
    Err(E),
}

fn classify(c: u8) -> int {
    return match c {
        case '0'..='9' => 1,
        case 'a'..='z' => 2,
        case 'A'..='Z' => 3,
        _ => 0,
    };
}

fn write_all<T: Writer + Drop>(out: T, data: []u8) -> usize {
    let mut writer = move out;
    defer writer.drop();

    return writer.write(data);
}
